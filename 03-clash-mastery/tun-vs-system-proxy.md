# TUN 模式 vs 系统代理：两种流量劫持方式

> 你在 Clash Verge 设置里看到两个开关：系统代理（System Proxy）和 TUN 模式。它们解决的是同一个问题，但方式完全不同。这篇讲清楚它们的本质区别。

## 1. 问题的本质：如何让应用的流量经过 Clash？

Clash 启动后只是一个在本地跑着的进程，默认监听几个端口（比如 mixed-port: 7897）。但你机器上的其他应用——浏览器、Cursor、git、npm——它们并不知道 Clash 的存在。

**你需要一种机制，把应用的网络流量"劫持"到 Clash 里去处理。**

这就像你在路口设了一个检查站（Clash），但如果不修路标（流量劫持机制），车（数据包）根本不会开到检查站来。

有两种根本不同的"修路标"方式：


## 2. 系统代理（System Proxy）

### 工作原理

Windows 有一个全局代理设置（设置 → 网络 → 代理），Clash Verge 开启"系统代理"时做的事情就是：

**把 Windows 的系统代理地址设为 `127.0.0.1:7897`（你的 mixed-port）。**

就这么简单。之后，**那些会读取系统代理设置的应用**在发送 HTTP/HTTPS 请求时，会先把请求发到 `127.0.0.1:7897`，也就是交给 Clash 处理。

### 关键限制

这里有两个"仅仅"：

**限制一：仅 HTTP/HTTPS 流量。** 系统代理是 HTTP 层面的设定。TCP 连接到任意端口、UDP 流量（比如游戏、语音通话、QUIC 协议）——系统代理完全不管。

**限制二：仅"听话"的应用。** 系统代理只是一个设置值，应用**可以选择不读它**。很多应用确实不读：

| 应用类型 | 是否走系统代理 | 说明 |
|---------|-------------|------|
| Chrome/Edge/Firefox | ✅ 是 | 浏览器是最乖的 |
| Cursor/VSCode | ⚠️ 部分 | Electron 应用，有自己的代理设置，行为不一致 |
| git (命令行) | ❌ 否 | 需要手动设 `http.proxy` 或环境变量 |
| npm/yarn/pip | ❌ 否 | 需要设环境变量 `HTTP_PROXY` / `HTTPS_PROXY` |
| curl | ❌ 否 | 需要 `-x` 参数或环境变量 |
| Docker Desktop | ❌ 否 | 有自己的代理配置 |
| 游戏 | ❌ 否 | 用 UDP，系统代理管不了 |
| UWP 应用 | ❌ 否 | Windows 沙箱限制，默认无法访问 loopback |

### 系统代理下的流量走向

```
                          系统代理 = 127.0.0.1:7897
                          ─────────────────────────

Chrome (读取系统代理)  ───→ 127.0.0.1:7897 ───→ Clash ───→ 规则 → 代理/直连  ✅
Edge   (读取系统代理)  ───→ 127.0.0.1:7897 ───→ Clash ───→ 规则 → 代理/直连  ✅

git    (不读系统代理)  ───→ 直接访问 github.com ──────────────→ 被墙  ❌
npm    (不读系统代理)  ───→ 直接访问 registry.npmjs.org ──────→ 被墙  ❌
Docker (不读系统代理)  ───→ 直接访问 docker.io ───────────────→ 被墙  ❌

游戏 (UDP 流量)       ───→ 系统代理根本不处理 UDP ────────────→ 直连  ❌
```

**作为开发者，这个覆盖范围远远不够。** 你的工作流里一大半工具（git、npm、Docker、Cursor 的部分功能）根本不走系统代理。


## 3. TUN 模式（推荐你使用的方式）

### 工作原理

TUN 是一种**虚拟网络设备**（TUN = network **TUN**nel）。Clash 开启 TUN 模式时：

1. **创建一个虚拟网卡**——操作系统层面多出一块网络适配器
2. **修改系统路由表**——告诉操作系统：所有流量都走这块虚拟网卡
3. **Clash 接管虚拟网卡**——所有进入虚拟网卡的流量都由 Clash 处理

这是在 OSI 模型的 **Layer 3（网络层/IP 层）** 操作的，比系统代理（应用层）低得多。在这一层，Clash 能看到并处理**所有 IP 流量**——TCP、UDP、ICMP，什么都不漏。

应用根本不需要"知道"代理的存在。它们正常发送数据包，数据包到达操作系统网络栈后，被路由表引导到 TUN 虚拟网卡，然后 Clash 接手。对应用来说完全透明。

### TUN 下的流量走向

```
                      TUN 虚拟网卡接管所有流量
                      ════════════════════════

Chrome     ──┐
Cursor     ──┤
git        ──┤
npm        ──┼──→ 操作系统网络栈 ──→ 路由表 ──→ TUN 虚拟网卡 ──→ Clash ──→ 规则 → 代理/直连
Docker     ──┤
游戏 (UDP) ──┤
任何应用   ──┘

                                    一个都跑不掉 ✅
```

### Windows 上的前置条件

TUN 模式需要修改系统路由表和创建虚拟网卡，这是操作系统级别的操作，普通用户权限做不了。在 Clash Verge 里的解决方案是安装 **Service Mode**——一个以管理员权限运行的后台系统服务，负责管理 TUN 设备。


## 4. 对比表

| 特性 | 系统代理 | TUN 模式 |
|------|---------|---------|
| **流量覆盖** | 仅 HTTP/HTTPS | 全部（TCP/UDP/ICMP） |
| **应用覆盖** | 仅主动读取代理设置的应用 | 所有应用，无差别 |
| **工作层级** | 应用层（告诉应用去找代理） | 网络层（直接在 IP 层劫持） |
| **需要管理员权限** | 否 | 是（需装 Service Mode） |
| **对系统侵入性** | 低（只改一个注册表值） | 高（创建虚拟网卡，改路由表） |
| **性能开销** | 几乎没有 | 略高（多一层虚拟网卡处理） |
| **配置复杂度** | 无需配置 | 中等（但 Clash Verge 封装了大部分） |
| **git/npm/Docker 能用吗** | ❌ 需要额外配置 | ✅ 自动覆盖 |
| **UDP 流量** | ❌ 不支持 | ✅ 支持 |
| **推荐场景** | 只用浏览器翻墙 | **开发者日常使用（你的场景）** |


## 5. TUN 模式配置（Clash Verge）

### 第一步：安装 Service Mode

Clash Verge → 设置 → Service Mode → 点 Install

安装成功后图标变绿。这一步只需要做一次。如果提示失败，用管理员身份运行 Clash Verge 再试。

### 第二步：开启 TUN

设置页面直接 toggle TUN 开关即可。

### TUN 配置参数（在 YAML 配置中）

```yaml
tun:
  enable: true
  stack: mixed
  dns-hijack:
    - any:53
  auto-route: true
  auto-detect-interface: true
```

**参数解释：**

**`stack`** — TUN 的网络栈实现方式，决定了数据包怎么被处理：

| stack 值 | 工作方式 | 特点 |
|---------|---------|------|
| `system` | 用操作系统原生网络栈 | 性能最好，但兼容性一般 |
| `gvisor` | 用 Google gVisor 的用户态网络栈 | 兼容性最好，但性能略差 |
| `mixed` | **TCP 用 system，UDP 用 gvisor** | **推荐。兼顾性能和兼容性** |

**`dns-hijack: any:53`** — 劫持所有 DNS 查询（目标端口 53 的流量），强制交给 Clash 内置的 DNS 模块处理。这是 TUN 模式正常工作的关键——如果 DNS 不经过 Clash，Clash 无法正确匹配基于域名的规则。

**`auto-route: true`** — 自动设置路由表，让所有流量走 TUN。不开这个就等于装了虚拟网卡但不让车开上去。

**`auto-detect-interface: true`** — 自动检测物理网卡，避免 TUN 流量死循环（Clash 自身发出的流量不能再回到 TUN，否则无限循环）。


## 6. 什么时候用系统代理就够了

虽然 TUN 更强，但有时候系统代理反而更合适：

- **你只用浏览器翻墙**，不用命令行工具 → 系统代理就够了，而且更轻量
- **TUN 和公司 VPN 冲突** → 两个都想接管全部流量，通常不能共存。退回系统代理是妥协方案
- **TUN 模式导致某些软件异常** → 一些安全软件、企业管理工具可能和 TUN 冲突
- **临时回退** → TUN 出了问题一时修不好，先开系统代理保证浏览器能用

**实际操作建议：** 日常开 TUN 模式。如果遇到问题，先切到系统代理保证基本可用，再慢慢排查 TUN 的问题。两个开关不要同时开——虽然技术上可以，但没有意义且可能造成混乱。


## 7. 常见问题

### "开了 TUN 后所有网都断了"

最常见的原因：

1. **DNS 配置有问题。** TUN 模式依赖 Clash 接管 DNS。如果 Clash 的 DNS 配置不对（比如上游 DNS 不可达），所有域名都解析不了，看起来就是"断网了"。检查 `dns` 段配置，确保有可用的国内 DNS（如 `223.5.5.5`）作为 nameserver
2. **路由表冲突。** 有其他软件也在改路由表（VPN、网络管理工具），互相打架
3. **Service Mode 安装有问题。** 卸载重装试试

**急救方法：** 关掉 TUN 开关。如果 Clash Verge 已经无响应，打开 Windows 网络设置，手动删除那个虚拟网卡（搜"网络适配器" → 找到 Clash/Meta 的虚拟网卡 → 禁用）。

### "TUN 开关是灰色的/点不动"

Service Mode 没装好。去 Clash Verge → 设置 → Service Mode，确认已安装且状态为绿色。如果安装失败，关闭 Clash Verge，右键以管理员身份运行，再装。

### "开了 TUN 后和公司 VPN 冲突"

TUN 和 VPN 本质上都是在抢路由表的控制权——谁先写路由规则谁说了算。两个同时跑通常会互相覆盖。

**可能的解决方案：**
- 先连 VPN，再开 TUN，让 TUN 的路由规则覆盖 VPN 的（但 VPN 流量也会被 Clash 接管）
- 在 Clash 规则里把公司内网网段（如 `10.0.0.0/8`、`192.168.0.0/16`）设为 DIRECT，避免公司流量走代理
- 如果实在不行，用公司网络时关掉 TUN 退回系统代理

### "开了 TUN 后国内网站变慢"

你的规则（Rules）没有正确配置国内直连。TUN 模式下所有流量都经过 Clash，如果规则没有把国内流量匹配到 DIRECT，国内流量也会走代理节点绕一圈再回来，当然慢。

确保你的规则里有完善的国内直连规则（`GEOIP,CN,DIRECT` 是最基本的兜底，但最好有更细的域名规则集）。详见 [规则引擎](rule-engine.md) 那篇。

### "TUN 和系统代理要不要同时开？"

**不要。** 选一个就好。TUN 已经覆盖了所有流量，再开系统代理是多此一举。同时开不会报错，但两层劫持叠加可能导致某些边界情况的奇怪行为。
