# Clash 核心架构

> 先建立全局地图，再看每个配置字段，否则你永远在"瞎调"。

## 1. Clash 到底是什么

Clash **不是** VPN，**不是**浏览器插件，**不是**某个机场的专属软件。

Clash 是一个 **rule-based proxy client**（基于规则的代理客户端）。它做三件事：

1. **拦截**你电脑上应用发出的网络请求
2. **判断**这个请求应该走哪条路（直连？翻墙？屏蔽？）
3. **转发**请求到对应的出口，并负责协议转换和加密

用一句话概括：**Clash 是你的电脑和互联网之间的交通调度员。**

它不提供代理服务器——服务器由机场（如 NxOnEarth）提供。Clash 只负责"本地这一端"的拦截、路由决策和协议打包。

## 2. 核心组件

Clash 内部有五个核心组件，理解它们的分工是理解所有配置的前提。

```
┌─────────────────────────────────────────────────────────────────┐
│                        Clash 内核 (mihomo)                       │
│                                                                 │
│  ┌──────────┐  ┌──────────┐  ┌───────────┐  ┌──────────────┐  │
│  │ Inbound  │→ │   DNS    │→ │   Rule    │→ │ Proxy Groups │  │
│  │ (入站)    │  │ Module   │  │  Engine   │  │  (策略组)     │  │
│  └──────────┘  └──────────┘  └───────────┘  └──────┬───────┘  │
│                                                     │          │
│                                              ┌──────▼───────┐  │
│                                              │   Outbound   │  │
│                                              │   (出站)      │  │
│                                              └──────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 2.1 Inbound（入站）— 怎么拦截流量

Clash 必须先"接管"你电脑上的网络流量，才能做后续的事。接管方式有几种：

| 方式 | 原理 | 适用场景 |
|------|------|----------|
| **HTTP Proxy** | 应用主动把请求发给 Clash 的 HTTP 代理端口 | 支持 HTTP 代理设置的应用（浏览器、Cursor） |
| **SOCKS5 Proxy** | 同上，但用 SOCKS5 协议，能代理 TCP/UDP | 终端工具、部分客户端 |
| **Mixed Port** | 一个端口同时接受 HTTP 和 SOCKS5 | 最常用，Clash Verge 默认配置 |
| **TUN** | 创建虚拟网卡，在操作系统层面劫持所有流量 | 真正的全局代理，不依赖应用自觉设置代理 |
| **Redir/TProxy** | Linux 下的透明代理方式 | 路由器网关场景 |

**关键区别**：HTTP/SOCKS5 Proxy 需要每个应用"自觉"把流量发给 Clash（通过设置系统代理或在应用内配置代理地址）。TUN 则是在 OS 层面强制劫持，应用无法绕过。

这就是为什么有些应用（比如某些终端工具）开了"系统代理"还是不走 Clash——它们不读系统代理设置。解决方案就是开 TUN 模式。

### 2.2 DNS Module — Clash 自己的域名解析器

你可能会问：操作系统本身就有 DNS 解析，为什么 Clash 还要自己搞一套？

原因有两个：

**原因 1：规则匹配需要域名**

Clash 的规则里写的是 `DOMAIN-SUFFIX,openai.com,Proxy`。但如果操作系统已经把 `api.openai.com` 解析成了 IP 地址 `104.18.x.x`，Clash 拿到的就是一个 IP 连接请求——它不知道原始域名是啥，规则就没法匹配了。

所以 Clash 需要在 DNS 环节就介入，拿到域名信息。

**原因 2：DNS 污染**

GFW 的常见手段之一就是 DNS 污染——你问 `google.com` 的 IP 是什么，GFW 抢先给你一个假的回答。如果 Clash 用的是被污染的 DNS 结果，你的请求会被发到错误的地方。

Clash 的 DNS 模块支持两种模式：

- **fake-ip**：给每个域名分配一个假 IP（198.18.x.x 段），Clash 内部维护一个 fake-ip 到真实域名的映射表。应用拿到假 IP 发起连接，Clash 通过映射表查出域名，然后走规则匹配。
- **redir-host**：做真实的 DNS 解析，但 Clash 会记住域名和 IP 的对应关系。

> fake-ip 是主流方案，响应更快，也能避免 DNS 污染问题。代价是某些应用可能因为拿到假 IP 而行为异常（极少见）。

### 2.3 Rule Engine（规则引擎）— 大脑

规则引擎是 Clash 的核心决策层。它拿到一个连接请求后，从上到下逐条匹配规则，找到第一条命中的规则，把流量发给规则指定的 Proxy Group。

规则类型举例：

```
DOMAIN-SUFFIX,openai.com,AI-Proxy        # 域名后缀匹配
DOMAIN-KEYWORD,google,Proxy              # 域名包含关键词
IP-CIDR,91.108.4.0/22,Proxy              # 目标 IP 段匹配
GEOIP,CN,DIRECT                          # 目标 IP 属于中国，直连
PROCESS-NAME,cursor.exe,Proxy            # 发起请求的进程名匹配
MATCH,Final                              # 兜底规则，匹配一切
```

**规则是有序的，第一条匹配即停止。** 就像 `if-else if-else` 链。最后一条必须是 `MATCH`（兜底），否则未匹配的流量会被丢弃。

### 2.4 Proxy Groups（策略组）— 节点的逻辑分组

策略组不是具体的服务器，而是一组节点的"选择策略"。规则引擎的匹配结果指向的是策略组，策略组再决定具体用哪个节点。

| 策略组类型 | 行为 | 适用场景 |
|-----------|------|----------|
| **select** | 手动选一个节点 | 你想自己控制用哪个节点 |
| **url-test** | 定期测速，自动选最快的 | 日常使用，懒人首选 |
| **fallback** | 按顺序尝试，第一个能用的就用 | 保证可用性 |
| **load-balance** | 负载均衡，分散流量到多个节点 | 大流量下载 |

一个典型的策略组嵌套结构：

```
Rules 引用
   │
   ├── "AI" (select) ─────────── 手动选一个子策略组或节点
   │     ├── "美国节点" (url-test) ── 自动选最快的美国节点
   │     │     ├── US-Node-1
   │     │     ├── US-Node-2
   │     │     └── US-Node-3
   │     └── "日本节点" (url-test)
   │           ├── JP-Node-1
   │           └── JP-Node-2
   │
   └── "Final" (select)
         ├── Proxy
         └── DIRECT
```

### 2.5 Outbound（出站）— 真正发出请求

当策略组选定了一个具体的节点后，Clash 会用该节点配置的协议对请求进行加密打包，发送到远端代理服务器。

支持的出站类型：

- **代理协议**：Shadowsocks、VMess、VLESS、Trojan、Hysteria、Hysteria2、TUIC 等
- **DIRECT**：不走代理，直接连接目标（用于国内网站）
- **REJECT**：直接丢弃连接（用于广告屏蔽）

## 3. 数据流：一次请求的完整旅程

**场景**：你在 Cursor 里按了 Ctrl+L，Cursor 要访问 `api.openai.com`。

```
  Cursor                                                      OpenAI 服务器
    │                                                              ▲
    │ ① 发起 HTTPS 请求到 api.openai.com                           │
    ▼                                                              │
┌──────────────────────────────────────────────────────────┐       │
│                  Clash 内核 (mihomo)                       │       │
│                                                          │       │
│  ② Inbound 接收                                          │       │
│     TUN 模式：虚拟网卡拦截                                 │       │
│     系统代理：Cursor 读到代理设置，主动发给 Clash           │       │
│                          │                               │       │
│                          ▼                               │       │
│  ③ DNS 解析                                              │       │
│     fake-ip 模式：分配 198.18.x.x，记录映射               │       │
│     api.openai.com → 198.18.0.42（假 IP）                │       │
│                          │                               │       │
│                          ▼                               │       │
│  ④ Rule Engine 匹配                                      │       │
│     DOMAIN-SUFFIX,openai.com,AI  ← 命中！                │       │
│     → 交给策略组 "AI"                                     │       │
│                          │                               │       │
│                          ▼                               │       │
│  ⑤ Proxy Group 选择                                      │       │
│     "AI" 是 url-test 类型                                 │       │
│     → 自动选延迟最低的节点：US-Node-2 (89ms)              │       │
│                          │                               │       │
│                          ▼                               │       │
│  ⑥ Outbound 发送                                         │       │
│     用 VMess/Trojan/etc 加密请求                          │       │
│     发往 US-Node-2 的远端服务器                            │       │
│                          │                               │       │
└──────────────────────────┼───────────────────────────────┘       │
                           │                                       │
                           ▼                                       │
                    ⑦ 远端代理服务器                                 │
                       解密请求                                     │
                       以自己的 IP 访问 api.openai.com ─────────────┘
                       收到响应后加密返回
                           │
                           ▼
                    ⑧ 原路返回
                       Clash 解密 → Cursor 收到响应
```

整个过程对 Cursor 来说是透明的，它以为自己在直接访问 `api.openai.com`（或者通过一个简单的 HTTP 代理）。

### 关于 fake-ip 在这个过程中的作用

为什么不直接用真实 DNS 解析？假设你用运营商 DNS 解析 `api.openai.com`：

1. GFW 可能返回一个污染的 IP → 请求发到错误的地方
2. 即使 DNS 没被污染，解析结果需要等一个 RTT（往返时延）→ 慢
3. Clash 需要域名来匹配规则，但拿到 IP 后再反查域名不靠谱

fake-ip 模式下，Clash 立刻返回一个假 IP 给 Cursor（几乎零延迟），Cursor 拿到假 IP 发起连接，Clash 通过内部映射表查出域名，走规则匹配，然后由远端代理服务器去做真正的 DNS 解析。**DNS 解析的开销从你这端转移到了远端**——远端在墙外，不存在 DNS 污染问题。

## 4. Clash Meta vs 原版 Clash

**原版 Clash**（Dreamacro/clash）已于 2023 年删库停更。

**Clash Meta**（现更名为 **mihomo**）是社区接手维护的 fork，目前是事实上的主流内核。Clash Verge 使用的就是 mihomo。

Clash Meta/mihomo 相对原版的主要增强：

| 特性 | 原版 Clash | Clash Meta (mihomo) |
|------|-----------|-------------------|
| VLESS 协议 | 不支持 | 支持 |
| Hysteria/Hysteria2 | 不支持 | 支持 |
| TUIC 协议 | 不支持 | 支持 |
| Reality TLS 伪装 | 不支持 | 支持 |
| Rule Providers | 基础支持 | 增强支持（HTTP/File/Inline） |
| 进程名匹配 | 不支持 | 支持（PROCESS-NAME 规则） |
| Sub-Rule | 不支持 | 支持 |
| 更多 DNS 模式 | 基础 | fake-ip 增强、DNS mapping |

**实际影响**：你在配置文件或教程中看到 `VLESS`、`Hysteria2`、`PROCESS-NAME` 这些，都是 mihomo 独有的。如果用旧的原版 Clash 内核，这些配置会报错。

## 5. Clash Verge 在这个架构中的角色

```
┌──────────────────────────────────┐
│          Clash Verge (GUI)       │
│                                  │
│   订阅管理 ─── 下载并更新节点列表  │
│   配置编辑 ─── 修改/覆写配置      │
│   Mixin    ─── 注入额外配置       │
│   Script   ─── JS 脚本修改配置    │
│   状态面板 ─── 查看连接、日志      │
│   服务模式 ─── 以系统服务运行      │
│                                  │
│         ┌────────────────┐       │
│         │  mihomo 内核    │       │
│         │  (真正干活的)   │       │
│         └────────────────┘       │
└──────────────────────────────────┘
```

**Clash Verge 本身不处理任何网络流量。** 它是一个 GUI 壳子，负责：

1. **订阅管理**：下载机场（NxOnEarth）提供的订阅链接，解析出节点列表，写入配置文件
2. **配置生成**：把订阅配置 + 你的本地覆写（Mixin/Script）合并成一份完整配置，喂给 mihomo
3. **进程管理**：启动/重启 mihomo 内核进程
4. **UI 展示**：节点延迟测试、连接列表、日志查看、流量统计
5. **服务模式**：以 Windows Service 身份运行 mihomo，这样 TUN 模式能获得管理员权限

**理解这个分层很重要**：当你"改配置炸了"，问题出在 mihomo 内核解析配置文件的环节。Clash Verge 只是把你的修改传递给了 mihomo。所以排错的时候，应该看 mihomo 的日志，而不是 Clash Verge 的 UI 报错（后者往往只是 mihomo 的报错信息的转发）。

## 总结：你的心智模型

记住这个简化模型，后续所有配置文件的字段都能映射到这五个组件上：

```
你的应用 → [Inbound] → [DNS] → [Rules] → [Proxy Groups] → [Outbound] → 互联网
```

每个配置字段改的都是这条链上某个组件的行为。当你准备修改配置时，先问自己：**我改的是链条上的哪个环节？会影响上下游吗？**
