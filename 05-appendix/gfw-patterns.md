# GFW 封锁模式识别

> 知道 GFW **怎么**封你的，才能选对反制手段。盲目换节点、重启 Clash 是典型的 shotgun debugging——先诊断，再治疗。

## 为什么需要识别封锁模式

GFW 不是一种技术，而是一套**多层防御体系**，每层用不同的手段。你遇到的"网不通"可能是 DNS 污染、IP 封锁、协议识别等完全不同的原因。对策也完全不同：DNS 污染换节点没用，IP 封锁换 DNS 没用。

搞清楚是哪一层在搞你，才能精准反制。

---

## 1. DNS 污染

### 症状
- 无法解析被封域名，`nslookup` 返回错误的 IP
- 浏览器报 `DNS_PROBE_FINISHED_NXDOMAIN` 或解析到奇怪的地址
- 同一个域名，国内外解析结果不一致

### 检测方法

```powershell
# 用默认 DNS 解析（通常被污染）
nslookup google.com

# 对比：指定一个境外 DNS
nslookup google.com 8.8.8.8
```

如果默认 DNS 返回的 IP 在已知的污染 IP 段（如 `203.98.7.65`、`8.7.198.45`、`46.82.174.68` 等），基本确认是 DNS 污染。

> 注意：即使指定 `8.8.8.8`，传统 DNS 查询走明文 UDP 53，GFW 可以在中间注入伪造响应。所以 `nslookup google.com 8.8.8.8` 返回错误结果**不代表 8.8.8.8 被墙**，而是中间的 DNS 响应被劫持了。

### 影响范围
所有基于明文 DNS 的域名解析——不加密的 DNS 查询全部可以被污染。

### 反制措施
- 使用 DoH (DNS over HTTPS) 或 DoT (DNS over TLS)，让 DNS 查询加密
- Clash 的 DNS 模块：配置 `nameserver` 使用 DoH/DoT
- 使用 `fake-ip` 模式：Clash 根本不做真正的 DNS 解析，直接分配一个假 IP 映射到域名，后续由代理节点在远端解析

### 对你的影响
如果你的 Clash DNS 配置错误（比如 `nameserver` 里只有明文 DNS），这往往是**第一个被打的地方**。Cursor 连不上 AI → 先检查 DNS 配置。

## 2. IP 封锁

### 症状
- 连接特定 IP 超时，其他国际 IP 正常
- 换同一机场的不同节点，部分能连部分不能
- `ping` 或 `Test-NetConnection` 直接超时

### 检测方法

```powershell
# 测试某个节点 IP 的连通性
Test-NetConnection -ComputerName <节点IP> -Port <节点端口>

# 对比测试一个未被封的国际 IP
Test-NetConnection -ComputerName 1.1.1.1 -Port 443
```

如果节点 IP 完全不通，但其他国际 IP 正常 → 大概率是 IP 被封。

### 影响范围
仅影响被封的特定 IP。同一机场的其他节点（不同 IP）可能完全正常。

### 反制措施
- 切换到其他节点（不同 IP）
- 使用 CDN 中转（Cloudflare WARP、CDN relay），流量不直连被封 IP
- 等待机场运营商更换 IP（好的机场会主动轮换）

### 对你的影响
**"昨天还好好的节点今天突然不行了，但其他节点能用"** → 八成是这个节点的 IP 被封了。在 Clash Verge 里切个节点就行，不用折腾配置。

## 3. TCP RST 注入

### 症状
- 连接建立后**立即**被重置，报错 `Connection reset by peer`
- 能完成 TCP 三次握手，但一发数据就断
- 间歇性出现——有时连得上，有时被 reset

### 检测方法
需要抓包（Wireshark）才能确认：
- 看到来自中间路由的 RST 包，TTL 值与正常包不同
- RST 包的 timing 非常可疑（来得太快，比正常的服务器响应快）

对普通用户来说，如果连接能建立但传数据时立刻断开，且换协议（从 VMess 换到 Trojan）后恢复 → 大概率是 RST 注入。

### 影响范围
被 GFW 识别为代理流量的 TCP 连接。关键词：**识别**——GFW 不是对所有连接都注入 RST，只对它认为是代理流量的连接下手。

### 反制措施
- 使用抗检测能力更强的协议：Trojan（伪装成正常 HTTPS）、VLESS+TLS
- 使用基于 UDP 的协议：QUIC、Hysteria、TUIC（绕开 TCP RST 注入）
- 开启 TLS 1.3，减少握手信息泄露

### 对你的影响
Cursor 连接短暂建立后立刻断开，日志里看到 `connection reset` → 可能是 RST 注入。试试换协议或换 UDP 类节点。

## 4. SNI 检测

### 症状
- TLS 握手阶段就失败，还没传数据就被掐断
- 同一个 IP 访问某些域名正常，换个域名就不行
- 改了 hosts 文件绕过 DNS 污染后，仍然连不上

### 检测方法

```powershell
# 假设你已经通过其他方式拿到了 google.com 的真实 IP
# 直接用 IP 访问（不带 SNI）可能成功
# 但 curl 指定 SNI 为 google.com 时就会失败
curl --resolve google.com:443:<真实IP> https://google.com
```

如果直连 IP 可以通但指定 SNI 后不行 → SNI 检测。

### 影响范围
所有 TLS 连接中 SNI 字段包含被封域名的流量。SNI 在 TLS ClientHello 中以**明文**传输（TLS 1.3 之前的标准行为），GFW 可以直接看到你想连的域名。

### 反制措施
- 通过代理转发：让 GFW 只能看到你和代理服务器之间的 TLS，SNI 是代理域名而非目标域名
- ECH (Encrypted Client Hello)：加密 SNI 字段，但目前 GFW 已经开始封锁 ECH 连接
- 不要试图只靠改 hosts 绕过 DNS 污染——**DNS 污染 + SNI 检测是组合拳**

### 对你的影响
这解释了为什么"改 hosts 能解析到正确 IP 但还是连不上"。GFW 的防线不止一层，绕过 DNS 污染只是第一步，SNI 检测是第二步。所以你需要代理，不是 hosts hack。

---

## 5. 深度包检测 (DPI)

### 症状
- 代理一开始正常，用了一段时间后变慢或断开
- 同一种协议的所有节点同时出问题
- 流量特征明显的协议（早期 Shadowsocks、未混淆的 VMess）特别容易中招

### 检测方法
没有简单的检测方法。但可以通过排除法：
- 如果同一种协议的所有节点同时出问题，而其他协议正常 → 大概率是 DPI 识别了这种协议的流量特征
- 新建连接正常，但持续传输后被掐断 → GFW 在做流量分析

### 影响范围
具有可识别流量特征的代理协议。GFW 不需要解密你的数据，只需要通过包长度分布、时间间隔模式、握手行为等**统计特征**判断"这不像正常的 HTTPS 流量"。

### 反制措施
- 使用基于 TLS 的协议：Trojan、VLESS+XTLS（流量特征与正常 HTTPS 高度相似）
- 使用 QUIC 系协议：Hysteria2、TUIC（走 UDP，DPI 经验较少）
- CDN 中转：流量混入 CDN 的海量正常流量中
- 开启多路复用 (mux)：改变流量模式

### 对你的影响
**"之前一直用的协议突然全线挂了"** → GFW 可能学会识别这种协议了。不是你配置的问题，是协议层面的对抗升级。关注机场公告，该换协议换协议。

---

## 6. 主动探测 (Active Probing)

### 症状
- 新开的节点能用几小时到几天，然后被封
- 封的是服务器（所有端口都不通），不是单个端口
- 不同用户在差不多的时间发现同一个节点挂了

### 检测方法
普通用户难以直接检测。但如果你注意到：
- 节点的生存周期很短且规律（比如总是几天后挂）
- 机场频繁更新节点 IP
→ 大概率是被主动探测命中

### 影响范围
GFW 发现可疑 IP 后，会主动向该 IP 发送探测连接。如果服务器的响应"暴露"了自己是代理（比如对非法请求返回了代理特有的错误信息），GFW 就会封掉这个 IP。

### 反制措施
- Trojan 协议：对探测连接返回真实网页内容，伪装成普通 Web 服务器
- VLESS+Reality：直接 "借用" 真实网站的 TLS 证书，探测者看到的是合法网站
- 多服务复用同一端口：代理和真实网站跑在同一个端口上

### 对你的影响
**节点走马灯式地挂** → 机场可能正在被 GFW 主动探测。好的机场会用 Trojan/Reality 等抗探测协议，差的机场只能不停换 IP。

## 7. QoS / 流量限速

### 症状
- 国际连接变慢但**没有断开**，国内速度正常
- 下午/晚上特别慢，凌晨反而快
- 所有国际连接都慢，不只是代理

### 检测方法

```powershell
# 测试国内速度
# 用 speedtest.net 选一个国内服务器

# 测试国际速度
# 用 speedtest.net 选一个海外服务器

# 对比两者差异
```

如果国内 200Mbps、国际 2Mbps → ISP 级别的国际出口限速或拥塞。

### 影响范围
**所有**国际流量，不分代理不代理。这不是 GFW 的精准封锁，而是国际出口带宽的物理瓶颈或 ISP 的 QoS 策略。

### 反制措施
- 老实说，能做的不多。这是 ISP 层面的
- 试试不同时段上网（避开高峰期）
- 基于 UDP 的协议（Hysteria、TUIC）在丢包环境下表现更好
- 换 ISP（比如电信的国际出口通常比联通/移动好，但也看地区）
- 使用有 IPLC/IEPL 专线的节点（但贵）

### 对你的影响
**"下午3点突然变慢了"** → 先别怀疑 GFW，可能就是国际出口拥堵。用 speedtest 测一下国内 vs 国际速度差异就知道了。

## 诊断流程总结

遇到"网不通"时，按这个流程走：

```
你的代理还能用吗？
│
├─ 完全不通
│  ├─ 能解析域名吗？（nslookup）
│  │  ├─ 不能 / 返回错误 IP → DNS 污染
│  │  │  └─ 检查 Clash DNS 配置，确保用 DoH/DoT
│  │  └─ 能解析
│  │     ├─ 能 ping 通节点 IP 吗？
│  │     │  ├─ 不能 → IP 封锁
│  │     │  │  └─ 切换节点
│  │     │  └─ 能 ping 通
│  │     │     ├─ TCP 连接被 reset？ → TCP RST 注入
│  │     │     │  └─ 换协议（Trojan/VLESS）或换 UDP 协议
│  │     │     └─ TLS 握手失败？ → SNI 检测
│  │     │        └─ 确保走代理，不要直连
│  │
│  └─ 同协议所有节点都挂了？
│     ├─ 是 → DPI 识别了该协议
│     │  └─ 换协议类型
│     └─ 否，只有特定节点 → IP 封锁或主动探测
│        └─ 切换节点，观察新节点存活时间
│
├─ 能连但很慢
│  ├─ 国内速度正常吗？
│  │  ├─ 正常 → QoS / 国际出口拥塞
│  │  │  └─ 换时段，或用 UDP 协议（Hysteria）
│  │  └─ 也慢 → 本地网络问题，不是 GFW
│  │
│  └─ 特定网站慢，其他正常？
│     └─ 可能是规则配置问题，检查该网站走的是什么策略组
│
└─ 时好时坏
   ├─ 新连接正常，持续传输后断 → DPI
   └─ 节点几小时后死 → 主动探测
```

## 一句话版本

| 封锁手段 | 核心特征 | 第一反应 |
|---------|---------|---------|
| DNS 污染 | 域名解析就出错 | 检查 Clash DNS 配置 |
| IP 封锁 | 特定节点不通，其他正常 | 切节点 |
| TCP RST | 连上就断，`connection reset` | 换协议 |
| SNI 检测 | 改 hosts 也没用 | 确保走代理 |
| DPI | 同协议全挂 | 换协议类型 |
| 主动探测 | 节点活不过几天 | 用抗探测协议 (Trojan/Reality) |
| QoS 限速 | 慢但不断，国内正常 | 换时段或 UDP 协议 |

> **记住**：GFW 不是单一技术，而是多层体系。一次"网不通"可能是多种手段叠加的结果。按流程逐层排查，别一上来就重装 Clash。
