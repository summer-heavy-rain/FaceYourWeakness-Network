# 代理的本质：中间人

## 代理是什么

Proxy（代理）= **中间人**。

没有代理：
```
你的电脑 ─────────────────→ 目标服务器
```

有代理：
```
你的电脑 ───→ Proxy ───→ 目标服务器
```

你不直接跟目标服务器说话，而是告诉代理："帮我去问目标服务器，把回复带回来。" 目标服务器看到的是代理的 IP，不是你的。

这就是代理的全部核心概念。后面所有复杂的东西——加密、混淆、协议——都是在这个基本模型上叠加的工程细节。

---

## 为什么需要代理

### 1. 翻墙

GFW（Great Firewall）阻断你直接访问 Google、OpenAI 等服务器的连接。但如果你有一台在墙外的代理服务器，GFW 管不到代理服务器到目标网站之间的链路：

```
你 ──[墙内]──→ 代理服务器 ──[墙外]──→ Google
     GFW 在这里            GFW 管不到这里
```

翻墙的本质：**把被墙的流量伪装成正常流量，送到墙外的代理服务器上去。**

### 2. 隐私

目标服务器只能看到代理的 IP 地址，无法直接追溯到你。这不是绝对匿名（cookie、浏览器指纹等仍然可以追踪你），但至少在网络层隐藏了你的真实地址。

### 3. 缓存/加速

企业代理可以缓存频繁访问的内容来加速访问（CDN 也是类似思路）。对你个人翻墙场景不太相关，但这是代理在企业网络中的常见用途。

## 正向代理 vs 反向代理

### 正向代理（Forward Proxy）

```
Client ───→ Forward Proxy ───→ Target Server
```

**你主动选择使用代理。** 代理替客户端（你）去访问互联网。Clash 做的就是这件事——你的请求先到 Clash，Clash 根据规则决定走直连还是走代理节点。

### 反向代理（Reverse Proxy）

```
Client ───→ Reverse Proxy ───→ Backend Server
```

**服务器在自己前面部署代理。** 用户通常不知道也不关心反向代理的存在。

典型例子：
- **Nginx**：用户访问 `example.com`，Nginx 接收请求后转发给后端的 Node.js / Python 服务
- **Cloudflare**：用户访问某网站，流量先经过 Cloudflare 的 CDN 节点做缓存和安全防护

反向代理的目的是保护服务器、负载均衡、缓存加速——跟翻墙没关系。

> 你日常用 Clash 只涉及正向代理。但理解反向代理的概念在以下场景有用：当你 debug CDN 问题（比如 Cloudflare 返回奇怪的错误），或者当你部署自己的服务配置 Nginx 时。

## 代理 vs VPN

这两个词在中国被严重混用，但它们是不同的东西。

### VPN（Virtual Private Network）

- 在你的设备和 VPN 服务器之间建立一条**加密隧道**
- 工作在操作系统/网络层——**所有流量**都走隧道
- 你的设备被分配一个 VPN 内网 IP
- 设计目的：安全连接远程网络（公司内网、校园网），**不是为翻墙设计的**
- 常见协议：OpenVPN, WireGuard, IPSec

### Proxy（代理）

- 在应用层面路由特定流量
- 可以**按规则分流**——某些域名走代理，某些走直连
- 更轻量，不需要在 OS 层创建虚拟网卡
- **Clash 的规则系统就是代理相对于 VPN 的核心优势**

### Clash TUN 模式：模糊了边界

Clash 开启 TUN 模式后，会创建虚拟网卡接管所有系统流量——行为上跟 VPN 非常像。但底层用的仍然是代理协议（Shadowsocks、Trojan 等），并且保留了规则分流能力。

**TUN 模式 = 用 VPN 的方式捕获流量 + 用代理的方式处理流量。**

### 为什么大家都叫 "开 VPN"

历史原因。早期翻墙确实用 VPN（PPTP、L2TP），后来被 GFW 精准封杀，大家转向代理协议（SS、VMess、Trojan），但 "VPN" 的叫法已经固化。严格来说，Clash + 机场订阅 ≠ VPN，是代理。但约定俗成，别人说 "开 VPN" 你知道是怎么回事就行。

## 代理的工作模式

从"谁决定流量走不走代理"的角度，可以分三种模式：

### 1. Application-level Proxy（应用级代理）

应用自己显式地把流量发到代理。需要应用支持代理设置。

```
Browser (配置了 proxy=127.0.0.1:7897) ──→ Clash ──→ Internet
```

- 只有你配了代理的应用才走 Clash
- 没配的应用完全不受影响
- 典型场景：在 Cursor / VS Code 里设置 `http.proxy`

### 2. System Proxy（系统代理）

操作系统层面设置 HTTP/HTTPS 代理（Windows: Internet Options → Proxy），应用**可以选择尊重**系统代理设置。

```
OS 设置: HTTP Proxy = 127.0.0.1:7897
├── Chrome: 读系统代理 ✓ → 走 Clash
├── git: 不读系统代理 ✗ → 直连
└── curl: 不读系统代理 ✗ → 直连（除非设 HTTP_PROXY 环境变量）
```

问题：很多命令行工具和部分桌面应用**不读系统代理设置**，所以会漏掉。

### 3. Transparent Proxy / TUN（透明代理）

在网络层劫持流量，应用完全不知道代理的存在。

```
任何应用 ──→ 虚拟网卡(TUN) ──→ Clash ──→ 按规则分流
```

- 所有流量无一例外都经过 Clash
- 不需要任何应用做任何配置
- Clash Verge 的 TUN 模式就是这个
- 最省心，也是你目前用的方式

### 对比

| | Application Proxy | System Proxy | TUN |
|---|---|---|---|
| 覆盖范围 | 单个应用 | 尊重系统设置的应用 | 所有流量 |
| 配置复杂度 | 每个应用单独配 | 一处设置 | 开个开关 |
| 应用感知 | 知道自己走代理 | 知道 | 完全不知道 |
| 可靠性 | 确定生效 | 有的应用不听 | 确定生效 |
| 你的场景 | Cursor 手动设 proxy | Clash 默认开的 | TUN 开启后最省心 |

## 小结

| 概念 | 一句话 |
|------|--------|
| 代理 | 中间人，替你转发请求 |
| 正向代理 | 替客户端（你）访问互联网 |
| 反向代理 | 替服务器接收互联网请求 |
| VPN | 加密隧道，OS 层接管全部流量 |
| TUN 模式 | 透明代理 + 规则分流 = VPN 的捕获方式 + 代理的处理方式 |
| System Proxy | OS 层代理设置，但应用可以选择不理你 |
| Application Proxy | 手动告诉单个应用走代理 |
