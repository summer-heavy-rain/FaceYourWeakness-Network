# 翻墙协议演化史：从 Shadowsocks 到 Trojan

> 这篇讲的是 **Clash ↔ 远程代理服务器** 之间的协议——它们的设计目标都是同一个：**把你的流量安全地、不被 GFW 识别地送到墙外。** 每一代协议的诞生，都是为了解决上一代被 GFW 破解后暴露出的弱点。

---

## Shadowsocks (SS) — 开创者 (2012)

### 起源

Shadowsocks 由 clowwindy 于 2012 年创建，是第一个真正意义上为翻墙设计的轻量级代理协议。

### 工作原理

```
SS Client                          SS Server
   │                                  │
   │  1. 用预共享密钥(PSK)加密流量       │
   │─────────────────────────────────→│
   │                                  │  2. 解密，拿到真正的目标地址和数据
   │                                  │─────→ 目标网站
   │                                  │←─────
   │  3. 加密回传                       │
   │←─────────────────────────────────│
```

核心思路极其简洁：
- Client 和 Server 共享一个密码和加密算法
- Client 加密所有流量发给 Server
- Server 解密后转发给目标网站
- 返回的数据同样加密后送回 Client

### 为什么能对付 GFW

早期 GFW 主要通过**关键字检测**和**协议特征识别**来封锁（检测 VPN 协议的握手特征）。SS 的加密流量看起来就是一坨随机数据——没有固定的协议头、没有可识别的握手模式，GFW 不知道这是什么。

### GFW 的反击

GFW 逐渐学会了：

1. **流量统计分析**：SS 流量虽然看起来随机，但包的大小分布、时序模式有统计特征，跟正常 HTTPS 流量不一样
2. **主动探测（Active Probing）**：GFW 向疑似 SS 的服务器发送特制数据包。真的 SS 服务器会有特定的错误响应行为，暴露身份
3. **重放攻击检测**：利用协议设计中的弱点

### 现状

SS 配合现代 AEAD 加密（如 `aes-256-gcm`、`chacha20-ietf-poly1305`）仍然可用，但在 GFW 重点监控的网络上越来越容易被识别。

**ShadowsocksR (SSR)** 是 breakwa11 开发的 SS 分支，加入了混淆（obfuscation）功能——让流量看起来像 HTTP 或其他正常协议。但项目涉及一系列社区争议后基本被抛弃，现在不推荐使用。

## VMess — V2Ray 的核心协议 (2015)

### 起源

V2Ray 项目试图创建一个**模块化**的翻墙平台，VMess 是其核心协议。

### 相对于 SS 的改进

1. **UUID 认证**：不再是简单的预共享密钥，而是使用 UUID 做身份验证——安全性更高，不容易被暴力破解
2. **可替换的传输层**：VMess 的杀手特性——协议本身和传输方式解耦：

```
VMess 协议内容可以跑在不同的传输层上：

├── TCP（直接 TCP 连接，最简单）
├── WebSocket（伪装成 WebSocket 通信）
├── HTTP/2（伪装成 HTTP/2 流量）
├── gRPC（伪装成 gRPC 调用）
└── QUIC（走 UDP，减少延迟）
```

3. **VMess + WebSocket + TLS 组合**：

```
GFW 看到的：
  正常的 TLS 连接 → 里面是 WebSocket → 看起来就像访问一个普通网站

实际上：
  TLS 加密 → WebSocket 传输 → VMess 协议数据 → 你的真实流量
```

这个组合可以穿过 CDN（比如 Cloudflare），因为 CDN 只看到合法的 WebSocket 流量。即使 GFW 封了你代理服务器的 IP，流量走 CDN 的话，GFW 无法区分你的代理流量和其他百万个正常网站的 CDN 流量。

### 缺点

- 协议复杂，性能开销比 SS 大
- 曾被发现安全漏洞（时间侧信道攻击）
- 配置选项太多，容易配错

### VLESS — VMess 的简化版

VLESS 是 V2Ray 后续推出的精简协议：
- 去掉了 VMess 自身的加密层（既然外层已经有 TLS 了，VMess 再加密一次是多余的）
- 更轻量、更快
- 安全性完全依赖外层 TLS
- **VLESS + WS + TLS** 是目前主流组合之一

## Trojan — 伪装成 HTTPS (2019)

### 激进的设计思路

SS 和 VMess 的思路都是：发明一个新协议，然后想办法让它不被 GFW 识别。

Trojan 换了个思路：**根本不发明新协议。直接就是标准的 HTTPS 连接。**

### 工作原理

```
1. 搭建一个真实的 HTTPS 网站（比如一个博客），申请真的 TLS 证书

2. Trojan Server 监听 443 端口
   ├── 收到请求，检查是否包含正确的密码
   │   ├── 有密码 → 这是 Trojan 客户端 → 代理流量
   │   └── 没密码 → 这是普通访客/GFW 探测 → 返回正常网页
```

从 GFW 的视角：

```
GFW 尝试探测：连接这个服务器的 443 端口
→ 收到了一个正常的网页（博客/默认页面）
→ TLS 证书合法
→ 跟普通 HTTPS 网站没区别
→ 无法判定这是代理服务器
```

### 为什么极难检测

- **TLS 握手完全合法**：真实域名 + 真实证书 + 标准 TLS 1.3
- **主动探测无效**：GFW 来探测，看到的就是个正常网站
- **流量特征**：跟正常 HTTPS 流量一模一样（因为它本来就是 HTTPS 流量）
- GFW 要想识别 Trojan，唯一的办法是**解密 TLS**——但没有私钥就做不到

### 代价

- 需要一个真实的域名（用来申请 TLS 证书）
- 需要在代理服务器上部署一个真实的 Web 服务作为 fallback
- 比 SS 多了一些配置工作

> 对你来说，这些是机场（NxOnEarth）替你搞定的——你不需要自己搭建 Trojan 服务器。

## 协议对比

| 特性 | SS | VMess | VLESS | Trojan |
|------|-----|-------|-------|--------|
| 抗检测能力 | 中等 | 高（WS+TLS） | 高 | 非常高 |
| 速度 | 快 | 中等 | 快 | 快 |
| 搭建复杂度 | 简单 | 中等 | 中等 | 中等（需要域名+证书） |
| TLS 必须 | 否（可选） | 否（可选但推荐） | 推荐 | 是（强制） |
| 抗主动探测 | 低 | 中等 | 中等 | 高 |
| 设计哲学 | 加密随机化 | 模块化+可替换传输层 | VMess 去冗余 | 伪装成正常 HTTPS |

## 在你的机场中

你的 NxOnEarth 订阅大概率提供了多种协议的节点。在 Clash Verge 的节点列表里，每个节点旁边会显示协议类型（`ss`、`vmess`、`trojan` 等）。

### 选择建议

- **稳定性优先**：Trojan 或 VLESS+WS+TLS——抗检测能力最强
- **速度优先**：SS（AEAD）或 VLESS——协议开销最小
- **被封后的备选**：VMess+WS+TLS 过 CDN——即使服务器 IP 被封也能用

但 "最佳协议" 不是绝对的。取决于：
- 你的 ISP（不同运营商对不同协议的检测策略不同）
- 你的地理位置
- 当前 GFW 的封锁策略（会动态调整）

> 实际操作中，你不需要手动挑协议。Clash 的 `url-test` 或 `fallback` proxy group 会自动测试延迟，帮你选可用的节点。协议是什么不重要，**能连上、速度快**才重要。

## 演化脉络

```
         GFW 学会统计分析
SS (2012) ──────────────────→ VMess (2015)
 加密随机化                    模块化传输层，WS+TLS 伪装

         VMess 太重，冗余加密
VMess ────────────────────→ VLESS
                             去掉自身加密，依赖 TLS

         换个思路：别发明协议了
────────────────────────→ Trojan (2019)
                           直接就是标准 HTTPS

每一代都是被 GFW 逼出来的。GFW 进化，协议就进化。
```
