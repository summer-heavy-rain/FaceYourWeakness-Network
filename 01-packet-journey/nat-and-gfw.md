# NAT 与 GFW：为什么你需要翻墙

> 两个看起来毫无关系的东西，但理解了它们，你就理解了"翻墙"到底在翻什么。

---

## NAT — 网络地址转换

### 为什么需要 NAT

IPv4 地址只有大约 43 亿个。全球几十亿设备都要联网，地址根本不够用。

解决办法：**不是每台设备都需要一个公网 IP**。你家里的路由器有一个公网 IP，你家里所有设备共享这一个公网 IP 上网。

你家里的设备用的是**私有地址（Private IP）**，以下三个范围的 IP 是"保留给内部使用的"，在互联网上不可路由：

| 范围 | 最常见的场景 |
|------|------------|
| `10.0.0.0/8` | 公司/大型网络 |
| `172.16.0.0/12` | 不太常见 |
| `192.168.0.0/16` | 家庭/小型办公室 |

你的电脑 IP 大概是 `192.168.1.x`，你同事的也是 `192.168.1.x`。这些地址在互联网上是不被承认的——就像你在公司内部分机拨号可以互相打，但直接拨内部号码打不到外面。

**NAT（Network Address Translation）**就是路由器在你和互联网之间做的翻译工作。

### NAT 怎么工作

```
                       你的路由器
你的电脑                （NAT）              互联网
192.168.1.100:52341 ─────┐
                          │   公网 IP
你同事的电脑               ├── 223.104.5.67 ──────> api.anthropic.com
192.168.1.101:48872 ─────┘
```

当你的电脑（`192.168.1.100`）要发包到 `api.anthropic.com`：

1. **出去的时候**：路由器把源地址从 `192.168.1.100:52341` 改成 `223.104.5.67:12001`（公网 IP + 一个新端口号）
2. 路由器在内存里记下一条映射：`223.104.5.67:12001 ↔ 192.168.1.100:52341`
3. 数据包以公网 IP 的身份出发，在互联网上畅行无阻
4. **回来的时候**：服务器响应发到 `223.104.5.67:12001`，路由器查映射表，把目标地址改回 `192.168.1.100:52341`，转给你的电脑

你同事的包也一样，只是映射到不同的端口号（比如 `223.104.5.67:12002`）。一个公网 IP，靠端口号区分不同的内部设备。

### NAT 类型

NAT 有几种类型，从宽松到严格：

| 类型 | 行为 | 影响 |
|------|------|------|
| **Full Cone** | 只要映射建立了，任何外部 IP 都能通过该端口发数据进来 | 最友好，P2P/游戏/语音无障碍 |
| **Restricted Cone** | 只有你主动联系过的 IP 才能发数据回来 | 稍有限制 |
| **Port Restricted Cone** | 不但要 IP 匹配，端口也要匹配 | 限制更多 |
| **Symmetric** | 每连一个不同的目标，就分配一个新的端口映射 | 最严格，P2P 打洞困难 |

大多数家用路由器是 Restricted Cone 或 Port Restricted Cone。运营商级 NAT（你的 ISP 可能再做一层 NAT，叫 CGNAT）通常是 Symmetric，这对 P2P 和游戏联机很不友好。

### NAT 和代理的关系

为什么要讲 NAT？因为它直接关系到你的代理能不能工作：

- 你的代理服务器（NxOnEarth 的节点）有一个**公网 IP**，在香港/日本/美国。它不在 NAT 后面。
- 你的电脑在 NAT 后面，需要**主动连出去**才能建立映射。
- 代理工作的核心：你主动连代理服务器（NAT 允许），代理服务器代替你去访问被封锁的服务。
- 如果代理服务器也在 NAT 后面——那就完蛋了，你找不到它。所以代理服务器必须有公网 IP。

## GFW — Great Firewall 的工作原理

### GFW 是什么

GFW 不是一台防火墙。它是一个**分布式的审查系统**，部署在中国与国际互联网的边界（边界网关/出口路由器上）。

可以理解为：中国互联网有几个"大门"通向外面（北京、上海、广州等出口），GFW 就是蹲在每个大门上的检查站。**所有进出中国的流量都要经过它。**

### GFW 的检测手段

GFW 不是只会做一件事。它有一整套武器库，而且在持续进化：

#### 1. DNS 污染（DNS Poisoning）

已经在 [DNS 那篇](dns-the-phonebook.md#dns-污染dns-poisoning-你在中国最该关心的) 详细讲过。简单说：GFW 拦截你的 DNS 查询，抢先返回假 IP。

**特点**：最早期也最粗暴的手段，但很有效——因为 DNS 是一切的起点。

#### 2. IP 黑名单（IP Blacklisting）

简单粗暴：直接封锁已知的 VPN/代理服务器 IP。发往这些 IP 的包直接丢弃（blackhole），或者返回 ICMP unreachable。

**特点**：效果立竿见影，但 IP 可以换。所以这是一个猫捉老鼠的游戏——封了换，换了封。

#### 3. 深度包检测（Deep Packet Inspection / DPI）

GFW 不只看包头（IP、端口），还会**分析数据包的内容和特征**。

不同的协议有不同的"长相"。比如：
- OpenVPN 的握手包有固定的特征字节
- Shadowsocks 早期版本的流量特征是"完全随机"——但"完全随机"本身就是一个特征（正常的 HTTPS 流量不是完全随机的）

DPI 就像一个有经验的海关官员——你用黑色塑料袋把违禁品包起来，他虽然看不到里面是什么，但"用黑色塑料袋包起来"这个行为本身就很可疑。

**特点**：技术含量最高的手段，也是催生各种新代理协议的直接原因。

#### 4. SNI 检测

TLS 握手的 Client Hello 消息里有一个字段叫 **SNI（Server Name Indication）**，包含你要连接的域名——而且是**明文**的。

```
TLS Client Hello
├── Version: TLS 1.3
├── Cipher Suites: [一堆加密算法]
├── Server Name (SNI): api.anthropic.com   ← GFW 能直接读到这个
└── ...
```

GFW 只要看 SNI 就知道你要去哪个网站，不需要解密任何东西。

**特点**：TLS 协议设计上的一个"漏洞"（其实是历史遗留问题）。新的 **ECH（Encrypted Client Hello）** 标准正在解决这个问题，但还没有普及。

#### 5. 主动探测（Active Probing）

这是 GFW 最"聪明"的招数：

当 GFW 怀疑某个服务器是代理时，它会**主动去连接那个服务器**，伪装成普通客户端，试图触发代理行为。

- 如果服务器回应了代理协议的特征（比如 Shadowsocks 的握手），GFW 就确认这是代理服务器，封锁 IP
- 如果服务器回应的是正常的网页内容（比如 Trojan 协议的"回落网站"），GFW 就放过

这就是为什么 **Trojan 协议要求配置一个真实的网站作为回落**——当 GFW 来探测的时候，服务器要表现得像一个正常的 HTTPS 网站。

**特点**：这招让很多早期代理协议失效了。现代协议（Trojan、VLESS+Reality）的设计核心之一就是抵抗主动探测。

### 被 GFW 检测到之后会怎样

| 行为 | 表现 |
|------|------|
| **TCP RST 注入** | GFW 假装服务器发一个 RST（重置）包给你，你的电脑以为服务器主动断开了连接 |
| **连接超时** | 包被直接丢弃（黑洞），你的请求石沉大海，等到超时 |
| **IP 临时封锁** | 你的 IP 到目标 IP 的通信被暂时封锁（几分钟到几小时） |
| **降速** | 不完全封锁，但把你的连接速度降到几乎不可用 |

你在 Cursor 里看到的 `ETIMEDOUT`、`ECONNRESET`、`UNABLE_TO_VERIFY_LEAF_SIGNATURE`——很多时候背后就是 GFW 在动手。

## 为什么简单的 VPN 不够用

传统 VPN 协议（PPTP、L2TP、OpenVPN）是为**隐私保护**设计的，不是为**绕过审查**设计的。它们有明显的协议指纹：

| 协议 | 特征 | GFW 能否识别 |
|------|------|------------|
| PPTP | 使用 GRE 协议，端口 1723 | 秒封 |
| L2TP/IPSec | 使用 UDP 500/4500 | 秒封 |
| OpenVPN | 握手包有固定特征 | 几乎秒封 |
| WireGuard | UDP，有固定的握手特征 | 很快被识别 |

这些协议设计的时候根本没考虑过"有人会分析你的流量特征并主动封锁你"。它们假设的威胁模型是"路上有人偷听"，而不是"路上有人在检查站拦截你"。

## GFW 的演化与代理协议的军备竞赛

这是一场持续的技术对抗：

```
时间线:

2003-2006  关键词过滤
           └─ 对策: HTTPS 加密

2009-2012  DNS 污染 + IP 封锁
           └─ 对策: SSH 隧道 / VPN / 修改 hosts

2012       Shadowsocks 诞生
           └─ 流量加密，没有明显特征
           └─ GFW 开始用 DPI 检测"高熵流量"

2015-2017  GFW 升级 DPI
           └─ 能识别 Shadowsocks 的流量特征
           └─ 对策: ShadowsocksR（混淆插件）/ V2Ray（VMess）

2017-2019  VMess 协议
           └─ 更复杂的加密和混淆
           └─ GFW 开始主动探测

2019-2020  Trojan 协议
           └─ 核心思路: 不是让流量看起来"不像代理"
           └─ 而是让流量看起来"就是正常的 HTTPS"
           └─ 使用真实 TLS 证书，配置真实网站作为回落

2021-2022  VLESS + Reality / XTLS
           └─ 进一步消除代理特征
           └─ Reality: 甚至不需要自己的域名和证书

2022-2024  QUIC 系协议 (Hysteria / TUIC)
           └─ 基于 UDP 的 QUIC 协议
           └─ 性能更好，但 GFW 开始限制 UDP 流量

持续进行中...
```

每次 GFW 升级检测能力，社区就发明新的协议来绕过。每次新协议出现，GFW 又会研究它的特征来封锁。这就是所谓的"军备竞赛"。

你用的 NxOnEarth 节点，背后用的协议（VMess、Trojan、或者 Hysteria）就是这场竞赛的产物。

## 总结：为什么你需要"翻墙"

把 NAT 和 GFW 放在一起看：

1. **NAT 让你的设备藏在路由器后面**，共享一个公网 IP 上网。这本身没什么问题。
2. **GFW 在出口检查所有出境流量**，封锁它不想让你访问的服务。
3. **代理的本质**：你找一台在墙外有公网 IP 的服务器（代理节点），先跟它建立加密连接（这条连接看起来无害），然后让它代替你去访问被封锁的服务。
4. **代理协议的演化**：就是在不断回答一个问题——"怎么让代理连接看起来不像代理连接"。

```
你的位置:                    GFW:                     自由的互联网:

┌──────────┐               ┌─────┐                ┌───────────────┐
│ 你的电脑  │──加密隧道──────│ GFW │───看起来正常───>│ 代理服务器(HK) │
│ NAT 后面  │               │     │    放行 ✓      │ 有公网 IP     │
└──────────┘               └─────┘                └───────┬───────┘
                                                          │
                                                    ┌─────▼─────┐
                                                    │ 目标服务器  │
                                                    │ GitHub     │
                                                    │ Anthropic  │
                                                    │ Google     │
                                                    └───────────┘
```
